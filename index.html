1. The Screening Bottleneck: Cheap Shortcut vs. Noisy Reality

Physical qubits in quantum computers make errors constantly. To protect useful quantum information, a quantum error-correcting (QEC) code spreads a smaller number of reliable logical qubits across many noisy physical data qubits, surrounded by helper ancilla (check) qubits that repeatedly check for errors without reading the stored data.

Today, researchers and AI-driven discovery loops can propose thousands of candidate quantum LDPC (Low-Density Parity-Check) codes in hours. The catch is testing them: running a realistic circuit-level Monte Carlo simulation (building the noisy gate circuit in Stim and running a classical BP+OSD decoder on tens of thousands of noisy runs) is slow. Measuring just 242 small codes in M0 took 76.3 CPU core-hours.

So search loops screen candidates first using a fast algebraic shortcut — Φ = k · d² / n — and only simulate the highest-Φ picks. The problem? Φ ignores how messy the error-checking circuit is to run on noisy gates and how hard it is to decode.

2. Inside a Code: Tanner Graphs & Syndrome-Extraction Circuits

Every CSS quantum LDPC code is defined by two sparse binary parity-check matrices, H_X (catches phase-flip Z errors) and H_Z (catches bit-flip X errors). Instead of reading grids of 0s and 1s, researchers represent each matrix as a Tanner graph: a two-sided network connecting data qubits (circles) to parity checks (squares).

Why does qecscreen extract 28 graph and circuit features instead of relying only on n, k, and d_upper? Because how the Tanner graph is wired directly controls hardware noise and decoder difficulty:

  • Check weight (check_weight_mean): A weight-8 check needs twice as many sequential two-qubit CX gates per round as a weight-4 check, leaving data qubits sitting idle longer and amplifying hook errors.
  • Short cycles (cycle4_count, cycle6_count, girth): Closed 4-step loops in the Tanner graph bounce Belief Propagation messages back onto themselves, making the decoder stall and fall back to slow OSD search.
  • Connectivity (lambda2, n_components): Spectral expansion measures how well error clues spread across the graph.

3. Measuring Ground Truth: Adaptive Shots, LER Normalization & Censoring

To build trustworthy labels without wasting CPU hours on bad codes, qecscreen simulates every code under one pinned protocol (protocol_hash 6230a7a8…: uniform depolarizing noise at p = 0.002, Z-basis memory for r = d_upper rounds, Stim 1.16.0 + ldpc 2.4.1 BP+OSD order 10).

Each code runs in batches of 256 shots until it accumulates at least 100 logical failures, stopping at a hard cap of 40,960 shots. Why? Because the codes we most want to find — the ones with ultra-low error rates — take 20× to 40× more shots to reach 100 failures than an average code!

If a code hits 40,960 shots with fewer than 100 failures, we refuse to guess a noisy point estimate (INV-3). Instead, we mark it censored (true_ler = null), exclude it from regression training, and rank it conservatively by its 95% Wilson upper bound (true_ler_ub). Every non-censored rate is normalized to one fair per-round, per-logical-qubit scale (INV-4): true_ler = 1 − (1 − P_L)1 / (r · k).

5. Why Recall@30 Failed While Spearman Hit 0.871

How can a model track the global ordering of 242 codes at 0.871 Spearman, yet catch only 2 of the top 10? Two subtle effects — one about ML evaluation hygiene, one about QEC thresholds — explain the whole story.

First, random train/test splits are banned (INV-2) because codes from the same polynomial template are near-duplicates. Instead, M0 holds out one entire construction program (template) at a time. In M0, all 10 of the genuinely best codes belong to one single template, pair_2_2 — meaning one held-out fold had to extrapolate to all 10 winners without ever seeing a pair_2_2 example during training!

6. Scientific Guardrails & What Comes Next (M1–M4)

ML-for-science benchmarks are easy to break accidentally with data leakage, inconsistent units, or cherry-picked baselines. qecscreen enforces six core invariants in CONTRACT.md with automated pytest guards (427 default tests passing):

INV-1 · Truth vs. Surrogate

Predictions never mix with labels

true_* measurements and pred_* model outputs live in separate Parquet files. A model guess is never reported as a code's error rate.

INV-2 · Leakage Guard

Grouped splits only

train_test_split on code rows is banned by source-grep tests. Splits group by construction_program_id (and by code family from M2).

INV-3 · Censoring

Thin labels are bounds, not guesses

Fewer than 100 failures means censored = True and true_ler = null; excluded from regression fits and ranked by true_ler_ub.

INV-4 · Normalization

One LER formula everywhere

1 − (1 − P_L)^(1/(r·k)) lives exclusively in protocol.py, enforced by a self-tested source-grep guard.

INV-5 · Distance Honesty

Bounds never called exact

Randomized search yields d_upper (d ≤ d_upper). d_exact stays null unless proven exact; proxy is named phi_from_d_upper.

INV-6 · Protocol Hash

Never compare mixed protocols

Every row stores a SHA-256 protocol_hash. Metric and training entry points raise ValueError if two protocols are mixed.
